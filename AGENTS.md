# AGENTS.md — dsh-plugin-smart-commands

Standalone Cordis plugin. Entry is `src/index.ts` with named `name` / `inject` / `apply` and no default export.

## Commands

```sh
npm install
npm run typecheck
npm test
npm run build
```

`npm test` / Vitest may need host process spawn (esbuild). Do not treat a sandbox `EPERM` spawn as a product failure.

`graphify-out/` is a generated knowledge graph (`graph.html`, `GRAPH_REPORT.md`, `graph.json`), gitignored and local-only. On Windows, AST extract must use `extract(..., parallel=False)`: ProcessPool re-imports the driver script and empties the graph. `GRAPH_REPORT.md` records `built_at_commit` — compare it with `git rev-parse HEAD` before trusting the graph, but a matching commit is not sufficient: uncommitted working-tree changes are still in the graph (verified: 6 deleted `docs/*` files still hold 23 of 821 nodes), so also check that each node's `source_file` exists on disk. Query the existing graph with the interpreter recorded in `graphify-out/.graphify_python` — `& $py -m graphify query "<question>"`; no `graphify` on PATH is needed. Refresh code with `graphify update .` (AST only, no API cost, which is why the report's token cost stays 0). The Markdown corpus needs semantic extraction, and with no `GEMINI_API_KEY`/`GOOGLE_API_KEY` set that means dispatching the host agent as the extractor. A full rebuild of the whole repo takes one semantic chunk. Expect ~90 dangling-endpoint edges, but they are **not** a semantic-extraction defect: verified AST-only, they are unresolved imports of external packages (`ref_vitest`, `ref_node_fs_promises`, `ref_react`, …) plus a few `calls` edges keyed by absolute-path ids. The semantic pass is chunk-internal and self-consistent. The ~92 collapsed edges are multi-edge collapse (e.g. one `contains` edge per symbol location), also benign.

## Layout

- `src/loader/` — YAML frontmatter + dual-directory catalog (execution overlay + uncollapsed inventory). If user/project dirs resolve to the same path (cwd/`workspaceRoot` is `$HOME`, junction, or case-insensitive Windows match), scan once as `user` and refuse project writes. Settings mutations send the GUI's current workspace path (`ctx.workspaces` + current session); `TemplateLoader.retargetProject` then points project templates at `<workspace>/.dsh/commands`.
- `src/engine/` — args/`<if-model>`, model fallback+restore, chain DAG, runner, `ChainRunRegistry` (the detached chain-run table: one AbortController per run, step progress via `ChainExecutor.onStep`, one settle observer, plain-JSON snapshots only), and `run-summary.ts` (the settled-run report, a pure function of one `ChainRunRecord`)
- `src/run-format.ts` — root-level, layer-neutral `formatDuration` / `firstLine`, shared by the host report and the client dock (same reason `catalog-query.ts` lives at the root). Do not re-add a second duration formatter on either side.
- `src/host/dsh-adapter.ts` — wraps DSH `ctx.subagents.start(name, request)` and adapts the invocation `Agent` (`invocation.agent`) into `HostAgent.submit` (user-sourced, abort-guarded) and `HostAgent.notify` (plugin-sourced, never abort-guarded) via `followup()`. Duck-typed: the real DSH agent has no `submit` — before this adapter, in-session runs silently echoed the rendered prompt and never started a main-agent turn.
- `src/tools/` — three model-facing tools
- `src/plugin.ts` — `/smart` lists templates; each template also registers `/<name>`
- `src/remote/` — settings UI catalog API + optional Cordis `smartCommands` Typert gateway. Endpoint ids/methods/`typeSymbol`s live in `contract.ts`; host/`./remote` bind Zod from `schemas.ts`, the client `$mount` contribution binds hand-rolled parsers so the browser bundle stays Zod-free. `smartCommands/list` always takes `CatalogScope` (`workspaceRoot?`). The run pair (`listRuns`/`cancelRun`) binds a separate `SmartCommandsRunApi` under its own global symbol — the Gateway's `@Remote` methods cannot read instance fields (Cordis tracker proxy). Adding an endpoint in `contract.ts` propagates to all three bindings automatically — `tests/typert-manifest.spec.ts` derives the expected method order from `SMART_COMMANDS_ENDPOINTS`, so no test edit is needed (do not reintroduce a hard-coded method array there; a stale one silently passed review until 509dd7b added `listKeywords`/`writeKeywords`).
- `src/client/` — Web UI components (`settings.section` id `smart-commands`, `conversation.input.left` id `smart-commands.prompt-trigger`, and `conversation.input.dock` id `smart-commands.runs` = `RunDock`); bundled to `dist/client.js`. Editor/copy/import dialogs and prompt dropdown popovers must `createPortal` onto `document.body` with z-index above overlays (1000/1050); the settings panel uses `overflow: hidden`. The catalog is a selectable list, not a card grid. Project-origin tags show the workspace folder name (`sourceLabel`), not the generic「项目」label. Toolbar Export packs checked rows as a store-only zip (`user|project/<name>.md`). Import opens a drop-zone dialog (click or drag `.md` / zip / JSON), then a layer select and confirm; writes use the chosen origin. Prompt menu appends slash commands below the current composer draft, so consecutive prompt clicks stack downward. Keyword chips append via `appendKeywordToDraft` and must read the live composer through session-slot `useInput(s => s.draft)` + `inputActions.setDraft` — DSH's composer is Lexical (`[data-composer-input]`), `InputState` uses `draft` not `text`, and `document.querySelector('textarea')` is empty, so consecutive keyword clicks would otherwise overwrite. `RunDock`'s roster rules live in `run-view.ts` (`visibleRuns`): a live run is never hidden (it owns the only cancel control), an unopened settled row clears itself after `FINISHED_VISIBLE_MS`, an opened (pinned) row stays until dismissed, and dismissal is client-local state — the host still holds the row until its own retention window expires.
- `examples/` — template samples, not loaded automatically
- `cordis.patch.yml` — profile bundle insert for `dsh plugin --profile <name> add`

Project templates override user templates of the same relative name. Invalid files are omitted from the catalog and reported on `smart_command_list.errors`; `smart_command_manage` still fails the write.

## Invariants

- Delegation deeper than `maxDelegationDepth` (default 3) is rejected.
- `{outputs.name}` must refer to an earlier unique `as`.
- Manage tools write only `<workspace>/.dsh/commands`. The settings page Remote (`smartCommands.write` / `copy` / `remove`) may write user or project when the UI sends `origin`.
- Settings UI is a `dsh.client` lazy-CJS factory at `exports["./client"]`. Host Typert artifacts live at `./typert` and `./remote`. `exports["./typert"]` must include a string `default` (typert-loader ignores `import`-only conditionals). Client `$mount`s `TYPERT_REMOTE` then reads Cordis service `remote.smartCommands` via `ctx.get` / `ctx.inject` — never `ctx.remote.smartCommands`. Host `inject` stays `['tools']`; `apply` constructs `SmartCommandsGateway` on the plugin root `ctx` and `ctx.inject(['typert'])` to `register(TYPERT)` so Gateway claims `/api/smartCommands/*`. Do not probe `ctx.reflect`. Do not add inject/config to `cordis.patch.yml`. Host/`./remote`/client `$mount` descriptors share `src/remote/contract.ts`; `list` includes `CatalogScope.workspaceRoot` so settings mutations retarget `<workspace>/.dsh/commands`. Host `deleteTemplate` keeps `implementation: 'remove'`; client descriptors omit that alias.
- Changing `src/client/` requires `npm run build` (or `build:client`) and a refresh of the existing `dsh web` URL; starting another Vite server does not update this GUI. Host `src/` (loader, engine, remote gateway) is loaded from `dist/*.js` into the `dsh web` Node process at boot — `npm run build` alone is not enough; restart that process. A browser refresh only reloads `dist/client.js`.
- User slash commands `/<name>` are registered from the catalog and disposed on delete/reload. `/smart` and `/help` are reserved and are not overwritten by a template of the same name.
- Host command names must match `^[a-z][a-z0-9_-]*$`. Numbered/nested templates are mapped (`001-research` → `/research`, `review/code` → `/review-code`). `/smart` lists those mapped names and does not run templates. Catalog identities (`assertTemplateName`) must accept those file stems — `^[A-Za-z0-9][A-Za-z0-9_/-]*$` — so settings `read`/`copy`/`export` work on numbered templates the loader already listed.
- Template `model:` is a comma-separated list of model specs (`id`, `provider/id`, `provider/*`) resolved against every registered LLM provider (`listProviders` + `listModels`), not only the current session provider. If none of the listed specs exist, the command **falls back to the current session model** (`agent-default-model.provider/model`) — that miss-fallback is intentional, not a parse failure. Do not turn it into a hard error unless a dedicated task says so. Subagent runs pass both `provider` and `model`. Chain **step** `model:` is a single string forwarded as `agentOptions.model` (no `selectModel`, no `provider/id` split). `subagent` / `chain` paths do not `withModelOverride` the parent session; only in-session runs snapshot and restore.
- A non-empty `subagent` string other than `continuable` is DSH `persona` (chain `agent:` is the same). It is not `agentPreset` / agent-preset. In-process children still join the parent session's agent-preset; persona only shadows `deployment:persona`. Do not add a preset-selection field unless a dedicated task says so.
- Official install is `dsh plugin --profile <name> add <package-or-path>`. The package must keep `dsh.bundle.patch` pointing at `cordis.patch.yml`; without it, add only installs a plain dependency.
- `cordis.patch.yml` must stay a plain `- insert:` of `id` + `name`. Extra `inject`/`config` rows make dshmarket treat the install as a non-bundle dependency even when `dsh.bundle` exists. Re-run `dsh plugin --profile <name> add .` from this checkout after adding the bundle declaration so an existing `link:` install is reconciled into `dsh.profile.bundles`.
- Cordis `ctx` is a proxy: reading an undeclared service (`ctx.workspace`, `ctx.commands`, …) throws `cannot get property "…" without inject` and aborts boot. Use `ctx.get(name, false)` for optional services. `inject` stays `['tools']`; `commands` is still late-bound through `ctx.inject(['commands'], …)`. DSH `workspace` entities expose `path`, not `cwd`; `workspaceRootOf` also accepts `sandboxPolicy.workspaceRoot` before `process.cwd()`.
- Host `ctx.tools.register` requires `output: { schema, render, presentationMeta? }`. Forward that field from the adapter; omitting it aborts boot.
- `subagent: true` uses one-shot `ctx.subagents.start()` and disposes the run. `subagent: continuable` or `continuable: true` uses `startContinuable()` and returns `subagentId`; follow-ups are host `send_message`, not another `/command`.
- In-session template runs deliver the prompt as a user message via `Agent.followup(createUserMessage(...))` and settle the command immediately — never `await whenIdle()`: the composer keeps the slash claim in the input and locks editing for the whole `commands.execute` transaction, so a handler that blocks on the full LLM turn leaves a ghost command and a dead input (the model reply streams as an ordinary assistant message; the submit result text is empty). Only slash-command handlers adapt `invocation.agent` via `asHostAgent`; the model-facing `smart_command_run` tool keeps passing the raw agent so `submit` stays absent — submitting into the caller's own running turn would deadlock the agent loop.
- Subagent delegation must receive the ORIGINAL DSH agent, never the `asHostAgent` duck wrapper: DSH's `subagents.start` reads `parent.session.header` / `parent.ctx` / `parent.options.maxTokens`, and the wrapper causes "Cannot read properties of undefined (reading 'header')". `asHostAgent` keeps the real agent at `HostAgent.original`; `wrapDshSubagents` forwards `parent.original ?? parent` to `ctx.subagents.start` and `startContinuable`.
- A chain slash command must never be awaited: DSH's claimed-command transaction locks the composer while `InputState.phase` is `adjudicating`/`submitting` (`editable = live && !locked && !machineBusy`), and the shell only settles it when the handler's promise resolves. `CommandRunner.startDetached` therefore registers the run in `ChainRunRegistry` with the run's OWN AbortController, returns an "already started" result, and drives `run(request, runSignal, parent, runId)` in the background; `run` mirrors `ChainExecutor.onStep` into the registry only when `runId` is set. A template that cannot detach (no run table, no `invocation.agent.id`, or no `chain`) falls back to the blocking `run`. `runs.cancelAll()` runs on plugin dispose.
- Never write a custom session event (`agent.session.append('smart-commands/…')`). `SessionEventMap` is merge-extensible and the runtime accepts unknown types, but `Session.append` has no `ignorable` entry point and the persistence READ path rejects unknown non-ignorable types, so such a session can no longer be opened after a restart. `dsh-session-projection` units fold committed session events only, so a projection cannot carry live step progress either — progress travels through this plugin's own `listRuns` remote.
- `listRuns`/`cancelRun` deliberately carry no `cancellation: { parameter: 'signal' }` descriptor entry (the calls are instantaneous, and cancellation would force the SRC-mode signature to end in a literal `signal` parameter). Registry cancellation is synchronous; a cancelled run is terminal and a later `finish()` never flips it back. Cancel scope is the owning session — `RunDock` sends its own session id and never `workspaceRoot`, because the recorded root is the plugin's apply-time workspace and a client workspace switch would no longer match it.
- A settled detached run is reported back into its own session, and that report is load-bearing for two things at once: the chain's aggregate text has nowhere else durable to live, and the session otherwise never sees a `turn/start` (the rule the sidebar reads — see the last bullet). `ChainRunStartInput.onSettled` is the single observation point, invoked by `ChainRunRegistry.finish` (settled by its own work) and `cancel` (cancelled from the dock or by the command transaction's signal), **at most once per run**, and deliberately **not** by `cancelAll` — disposal terminates every run at once, and each report would wake a turn in sessions the plugin is being unloaded out from under. `CommandRunner.reportSettled` posts it through `HostAgent.notify`; a throwing observer is absorbed in both the registry and the runner, because a run that already settled must never be turned into a failure by the message describing it. `notifyOnRunSettle` (default `true`) is the escape hatch — off means the run panel is the only place the output appears.
- `notify` and `submit` are different messages on purpose and must not be merged: `submit` is the user's own template prompt (`source.kind: 'user'`, abort-guarded, so a cancelled transaction does not start a turn), `notify` is the plugin's report (`source: { kind: 'plugin', plugin: 'smart-commands', form: 'notice', summary: <first line, ≤120 chars> }`, never abort-guarded because it describes work that already happened). The `plugin` source is what makes the transcript render a collapsed `smart-commands` context row instead of a user bubble; `form: 'notice'` is the same shape `dsh-plan-mode` uses for its narration. Both go through `Agent.followup(...)` and neither may `await whenIdle()`.
- Known open items and their options live in `docs/chain-run-followups.md`. Since option A landed, a detached chain's outcome is durable in the session and its session leaves `blank`; what remains is (a) the DSH-level rule that a session whose FIRST input is any *other* slash command stays `blank` (only `turn/start` flips it, `dsh-api-session-controller/lib/types/list.js:29`) and is hidden from the sidebar unless it is the current session — not a plugin bug, not introduced by detached runs, and worth an upstream issue; (b) the still-unverified split between a stale client-side `blank` and the 5-row fold; (c) one-shot `subagent:` templates still block their handler.
